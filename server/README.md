# فنون عدن — quiz API v2

The original GitHub Pages quiz calls `POST /api/quiz-submit` on the existing API host. The browser sends no Telegram/WhatsApp credential. Server validation recomputes the current eight-question quiz result and context-specific book from the same trusted `quiz-content.js` and `quiz-engine.js` release files as the browser.

Required request fields: `submissionId` (UUID), `name`, `phone`, `answers` (all eight question IDs and option IDs), `src`, `consent:true`, `website:""`, `elapsedMs` (integer, 8 seconds–7 days). Client retries must reuse the UUID and identical payload. Added fields, legacy answers, injected message text/destination, and client-computed results are rejected.

`202 {ok:true,accepted:true,submissionId,state:"queued"}` means the request and three independent jobs were committed to SQLite. It does **not** assert WhatsApp delivery or a successful Supabase insert. A duplicate identical UUID is acknowledged without new jobs; an altered UUID payload gets 409. A second UUID for the same phone within six hours gets 429. Limits: five accepted submissions/IP/hour, 100 global/hour and 500 global/day, including across service restarts. Client IP headers are trusted only behind the local nginx proxy. Origin locking is browser protection, not authentication; these limits also bound API abuse from other clients.

The outbox independently saves the exact eight existing `quiz_leads` fields, sends a fixed Telegram admin alert to `TG_CHAT`, and sends a fixed WhatsApp welcome to the validated phone. The WhatsApp welcome includes the current result label, free PDF, server-selected book and community link. No promised drip campaign or unverified testimonial is included.

Durability: SQLite WAL + synchronous FULL, transactional acceptance/idempotency/rate checks/jobs. A job is marked `processing` before its network request. Provider acceptance IDs are retained, without claiming delivery. Explicit 429 rejections are automatically retried (at most four attempts). For Supabase storage only, DNS lookup failures with `cause.code` ENOTFOUND/EAI_AGAIN retry every five minutes, at most 24 attempts (about two hours), because no connection was established. Timeouts, other network errors, invalid success responses and server errors become `unknown`, since their side effects cannot safely be ruled out. Messaging DNS failures remain `unknown`. On restart interrupted `processing` jobs become `unknown`, and pending jobs resume. Unknown jobs require a human to reconcile provider logs before a new send; no generic replay/send API is exposed. Do not run multiple worker service instances against this database: one systemd process owns the queue and restart recovery.

Node >=22.13 with `node:sqlite` (production Node24). `npm ci`, place protected `.env` using `.env.example`, copy both trusted quiz JS files to `QUIZ_SOURCE_DIR`, then `npm test` and `npm start`. Set a persistent `RATE_HASH_KEY`. The existing Supabase insert-only public anon key can be supplied as `SUPABASE_KEY`; service-role access is unnecessary. `.env`, SQLite files and logs must stay out of the public site/commits. Database directory is mode700 and database600; restrict backups likewise. Logs contain only fixed event/status codes, never request bodies, phone/name, secret URLs, or raw provider errors. Keep request body logging disabled in nginx/application monitoring.

`npm run check:providers` only calls Telegram getMe/getChat and WhatsApp status. It never sends messages or saves a lead. `npm run outbox:status` prints aggregate job states only. Provider API references: [WaSender send-text response](https://api.wasenderapi.com/api-docs/messages/send-text-message), [WhatsApp status](https://api.wasenderapi.com/api-docs/sessions/get-whatsapp-session-status), [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage).

For deployment, proxy the exact `/api/quiz-submit` path (including OPTIONS) to localhost3010, set a 4k nginx body limit, preserve Origin/Content-Type headers, and set X-Forwarded-For from the verified client address. Health is localhost `/health`. Keep `.env`, `data/`, and trusted quiz source outside public web roots. Stop the single service gracefully before switching release files; do not copy a live SQLite database without SQLite's backup procedure. Operational retention of local leads/backups must match the owner's existing retention policy; unknown jobs should be reviewed before deletion.
